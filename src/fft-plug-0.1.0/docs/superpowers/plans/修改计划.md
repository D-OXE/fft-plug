# fft-plug 修改计划

> 基于当前 `fft-plug.tar(1).zst` 实现制定。
>
> 本轮目标不是重写项目，而是在 **4K / 160 Hz** 显示环境下，保留当前流畅度的同时，让频谱动画更接近用户观察到的 Wallpaper Engine Corsair 风格：**起落更利落、鼓点更有冲击感、减少“黏”和“软”**；同时降低不必要的 CPU 唤醒与渲染开销。

---

## 1. 本轮目标

本轮只解决四类问题：

1. **动画响应**：去掉当前重复的 attack/release 平滑，使柱体更有冲击感。
2. **160 Hz 显示**：不降低显示器刷新率，不把渲染锁到 60/120 Hz；视觉更新继续跟随 160 Hz frame clock。
3. **CPU 占用**：减少无意义的 160 Hz tick、空闲轮询和重复 CPU 工作，但不以牺牲动画流畅度为代价。
4. **参数结构**：把“动态风格”从散落的魔法常量整理成可调 profile，便于后续在 `soft / balanced / punchy` 之间切换。

本轮 **不做**：

- 不迁移 GTK → SCTK/原生 Wayland；
- 不重写 PipeWire；
- 不切 Vulkan/wgpu；
- 不加入 Bloom/Glow/粒子；
- 不大规模重构目录；
- 不为了 CPU 占用降低 4K/160 Hz 的显示设置。

GTK/SCTK 迁移属于另一条独立工作流，应该等动画与性能基线稳定后再做，避免同时更换 shell 层和动画模型，导致问题难以定位。

---

## 2. 当前实现基线

### 2.1 DSP

当前默认参数：

```text
FFT_SIZE      = 4096
HOP_SIZE      = 512
BAND_COUNT    = 64
MIN_FREQ      = 20 Hz
MAX_FREQ      = 20 kHz
MIN_DB        = -80 dB
ATTACK        = 45 ms
RELEASE       = 220 ms
```

在 48 kHz 音频下：

```text
FFT 窗口长度 ≈ 85.3 ms
DSP 更新周期 ≈ 10.67 ms
DSP 更新率   ≈ 93.75 Hz
```

4096 FFT 本身保留。它提供了不错的低频分辨率，也是当前频谱观感稳定的重要原因。

### 2.2 Renderer

当前 renderer 又执行了一次：

```text
attack  = 45 ms
release = 220 ms
```

因此真实链路是：

```text
PCM
 ↓
4096 Hann FFT
 ↓
DSP attack/release 45/220 ms
 ↓
SpectrumSnapshot
 ↓
Renderer attack/release 45/220 ms
 ↓
OpenGL
```

这是当前“很丝滑，但偏软”的主要原因。

### 2.3 显示刷新

当前 GTK `add_tick_callback()` 跟随 display frame clock。

4K / 160 Hz 环境下，活动期间 renderer 最多约执行：

```text
160 render frames / second
```

而 DSP 只有约：

```text
94 spectrum snapshots / second
```

因此 renderer 的职责应该是：

> 在 160 Hz 下把约 94 Hz 的 DSP 数据显示得连续，而不是再做一遍长时间 attack/release。

# 3. 第一优先级：去掉重复动态平滑

## 3.1 修改 `src/render/mod.rs`

当前：

```rust
let time_constant = if target >= *displayed { 0.045 } else { 0.22 };
let alpha = 1.0 - (-elapsed_seconds / time_constant).exp();
*displayed += (target - *displayed) * alpha;
```

这等价于在 DSP 的 attack/release 后又串联一个同样的低通系统。

### 修改原则

Renderer **不再决定音乐动态**。

DSP 负责：

```text
attack / release
峰值响应
频段动态
```

Renderer 只负责：

```text
94 Hz snapshot → 160 Hz 屏幕
```

### 推荐实现

保留：

```rust
previous_levels
current_levels
```

新 snapshot 到来时：

```text
previous = 当前显示目标
current  = 新 snapshot
snapshot_age = 0
```

在每个 160 Hz frame 中做一个很短的、**对称的视觉插值**：

```text
visual_interpolation = 6~12 ms
```

第一版建议：

```text
8 ms
```

它不是音乐 attack/release，只用于避免 93.75 Hz → 160 Hz 时出现轻微阶梯感。

如果实机上直接画 DSP snapshot 已经足够平滑，可以进一步完全取消 renderer level smoothing。

### 验收

鼓点出现时，柱体应明显比当前版本更快抬升；低频鼓点结束后不应再出现接近一秒的“拖尾黏滞感”。

---

# 4. 第二优先级：调整 DSP 为 Punchy 动态

当前 DSP：

```text
attack  = 45 ms
release = 220 ms
```

对柔和视觉很合适，但距离“有冲击感”的风格偏慢。

## 4.1 第一轮参数

建议先改为：

```text
attack  = 15 ms
release = 120 ms
```

原因：

- 15 ms：鼓点和瞬态能快速抬升；
- 120 ms：仍保留连续性，不会像裸 FFT 一样抖动；
- 4096 FFT 本身已有约 85 ms 的观察窗口，不需要再设置很慢的 attack。

### 第二轮候选

如果仍偏软：

```text
attack  = 8~12 ms
release = 80~100 ms
```

如果变得太抖：

```text
attack  = 18~25 ms
release = 130~160 ms
```

不要一次跳到：

```text
attack = 0
release = 0
```

否则会破坏当前已经比较好的稳定性。

---

# 5. 引入 Dynamic Profile

不要继续把动态参数写死在 DSP 和 renderer 内。

建议增加：

```rust
pub enum DynamicsProfile {
    Soft,
    Balanced,
    Punchy,
}
```

对应初始参数：

| Profile | Attack | Release | 用途 |
| --- | ---: | ---: | --- |
| Soft | 45 ms | 220 ms | 当前风格附近 |
| Balanced | 25 ms | 150 ms | 日常默认候选 |
| Punchy | 15 ms | 120 ms | Corsair 风格候选 |

本轮默认改为：

```text
Punchy
```

CLI 可以暂时只增加：

```bash
fft-plug --dynamics punchy
```

不需要做配置 GUI。

---

# 6. 第三优先级：增加瞬态冲击，但不要破坏 FFT 稳定性

如果仅靠 15/120 ms 仍然觉得“不够顶”，不要首先把 FFT 从 4096 降到 2048。

4096 FFT 对低频视觉有价值。

更合理的是额外计算一个轻量的 **transient / spectral-flux accent**。

## 6.1 简单方案

记录上一帧原始 band level：

```text
raw_prev[i]
raw_now[i]
```

计算只关注上升：

```text
flux[i] = max(raw_now[i] - raw_prev[i], 0)
```

最终目标：

```text
target = base_level + transient_gain * flux
```

然后 clamp 到 `[0, 1]`。

初始：

```text
transient_gain = 0.15 ~ 0.30
```

这样：

- 平稳持续音不会被无限放大；
- kick/snare/bass 瞬态会更明显；
- 不需要缩短 FFT 窗口；
- 不需要破坏频率分辨率。

### 注意

这是第二阶段优化。

必须先完成：

```text
去掉 renderer 双重 smoothing
+
DSP 15/120 ms
```

实机比较后，再决定是否加入 transient accent。

# 7. 160 Hz 渲染策略

用户明确使用：

```text
4K / 160 Hz
```

本项目不得通过“限制到 60 Hz”来解决 CPU 占用。

## 7.1 活动期间

继续使用 GTK frame clock：

```text
160 Hz display
  ↓
160 Hz render opportunity
```

这样可以保留当前丝滑感。

DSP 仍然约 94 Hz：

```text
PipeWire → DSP ≈ 94 Hz
Renderer       = 160 Hz
```

Renderer 使用短插值连接 snapshot。

## 7.2 Sleeping 期间

当前永久注册的：

```rust
area.add_tick_callback(... Continue)
```

即使不 `queue_render()`，tick callback 本身仍持续随 frame clock 唤醒。

建议改成 **动态 tick 生命周期**：

```text
Active / Decaying
        ↓
安装 tick callback
        ↓
160 Hz render

Fade complete / Sleeping
        ↓
移除 tick callback
        ↓
GTK 主线程不再被 160 Hz 动画 tick 唤醒

新音频 wake request
        ↓
重新安装 tick callback
```

这不会降低播放时 160 Hz 的动画质量，却能明显改善真正空闲状态的 CPU 唤醒。

---

# 8. DSP Worker 的空闲唤醒

检查当前 worker 是否仍存在类似：

```rust
thread::park_timeout(Duration::from_millis(...))
```

的周期轮询。

如果存在，应继续向事件驱动收敛：

```text
PipeWire producer 写入 FIFO
        ↓
如果 consumer sleeping
        ↓
unpark DSP worker
```

DSP 无数据时：

```rust
thread::park();
```

而不是每 1~2 ms 自己醒一次。

目标：

```text
无音频：CPU 几乎不因 DSP polling 被唤醒
有音频：数据到达即唤醒，不增加可见延迟
```

---

# 9. OpenGL 路径：本轮不做过度优化

当前 Bars 模式只有 64 band，每帧约：

```text
64 × 6 vertices
```

即使 160 Hz，顶点数据量也非常小。

因此本轮 **不做**：

```text
Vulkan
persistent mapped buffer
复杂 instancing 系统
compute shader
GPU FFT
```

可做一个低风险小优化：

### VBO 预分配

`realize()` 时按最大 bar/curve 顶点容量：

```rust
glBufferData(..., max_size, nullptr, GL_STREAM_DRAW)
```

每帧：

```rust
glBufferSubData(...)
```

避免每个 160 Hz frame 都重新定义 buffer storage。

但这属于 P2；只有 release profiling 显示 GL upload/driver 占比明显时再做。

---

# 10. 4K 下的频段数量

当前：

```text
64 bands
```

在 3840 px 宽下，每 band slot 约：

```text
3840 / 64 = 60 px
```

视觉上柱体会比较粗。

本轮动画修复完成后，可以单独测试：

```text
64
96
128
```

建议候选：

```text
96 bands
```

理由：

- 4K 横向密度更自然；
- 仍远不足以构成 DSP/GL 性能压力；
- 比 128 更容易保留“有重量的柱子”。

但不要和动画参数在同一次 commit 中修改，否则不利于判断观感变化来自哪里。

---

# 11. 关于 FFT 4096 是否要缩短

本轮 **保留 4096**。

虽然：

```text
4096 / 48kHz ≈ 85 ms
```

会产生一定时间平均，但它同时提供了当前较稳定的低频表现。

真正造成当前过软的主要原因是：

```text
DSP 45/220
+
Renderer 45/220
```

不是 4096 FFT 一项。

只有在去掉双重 smoothing、改成 punchy profile 后仍觉得瞬态明显迟钝，才建立 A/B 实验：

```text
A: FFT 4096 / hop 512
B: FFT 2048 / hop 256 或 512
```

比较：

```text
鼓点响应
低频稳定性
频率定位
CPU
视觉抖动
```

不能仅凭“窗口短 = 更快”直接替换。

# 12. 推荐实施顺序

## Commit / Step 1：删除 Renderer 第二层 attack/release

只改 renderer 动态，不改 DSP 参数。

验证：

```text
当前 45/220 DSP
Renderer 不再 45/220
```

观察冲击感变化。

---

## Commit / Step 2：新增 Punchy DSP profile

加入：

```text
Soft      45 / 220 ms
Balanced  25 / 150 ms
Punchy    15 / 120 ms
```

默认 Punchy。

验证各种音乐类型：

```text
kick-heavy electronic
rock drums
vocal / acoustic
持续低频 bass
```

---

## Commit / Step 3：160 Hz renderer 短插值

如果直接 snapshot 在 160 Hz 下出现肉眼可见阶梯：

加入：

```text
6~12 ms visual interpolation
```

禁止重新加入 100~200 ms renderer release。

---

## Commit / Step 4：动态注册/移除 GTK tick

目标：

```text
Active     → 160 Hz
Decaying   → 160 Hz
Sleeping   → no frame tick
Wake       → restore 160 Hz
```

---

## Commit / Step 5：DSP worker 事件唤醒

去除高频 timeout polling。

---

## Commit / Step 6：可选 transient accent

只有前面完成后仍缺乏冲击感，才加入 spectral flux / positive delta accent。

---

## Commit / Step 7：4K band density A/B

独立比较 64 / 96 / 128 bands。

# 13. Debug/性能验收

必须用：

```bash
cargo build --release
./target/release/fft-plug --debug
```

Debug build 的 CPU 数字不作为性能验收依据。

记录：

```text
显示模式: 3840×2160 @ 160 Hz
音频采样率
DSP frame rate
render frame rate
PipeWire callback count
PCM overruns
CPU active
CPU silent
内存
```

## 建议工程目标

以下是目标，不是未测量前的硬性保证：

```text
播放时：
- render 能接近 160 Hz
- DSP 约 94 Hz（48k / hop512）
- 不发生持续 PCM overrun
- CPU 明显低于当前 debug 2%

静音并 fade 完成后：
- 不持续 160 Hz redraw
- DSP 不高频 polling
- CPU 接近空闲
```

本轮性能优化的原则：

> **不通过降到 60 Hz/120 Hz 换取 CPU。**

首先消灭无效唤醒、重复平滑和重复工作。

# 14. 本轮最终预期视觉

当前：

```text
声音瞬态
   ↓
缓慢抬升
   ↓
很顺滑
   ↓
较长拖尾
```

目标：

```text
声音瞬态
   ↓
快速抬升 / 有冲击
   ↓
160 Hz 连续运动
   ↓
较快但自然地回落
```

不是追求：

```text
生硬跳变
疯狂抖动
裸 FFT
```

而是：

> **保留当前版本的丝滑感，但把动态从“柔软”调整为“紧、快、有重量”。**

# 15. 建议修改后的默认参数基线

第一轮推荐：

```text
Display          = 4K / 160 Hz native
FFT              = 4096
Hop              = 512
Bands            = 64（暂不改）
Frequency        = 20 Hz ~ 20 kHz
DSP Attack       = 15 ms
DSP Release      = 120 ms
Renderer A/R     = 删除
Visual Interp    = 0~8 ms，按实机决定
Sleep Render     = fade 完成后停止 tick
Wake             = 音频事件重新启动 render
```

如果这套基线已经达到预期，就不要继续叠加复杂算法。

如果仍觉得缺少 Corsair 风格的瞬态冲击，再进入：

```text
transient / spectral-flux accent
```

而不是继续暴力缩短 release 或降低 FFT size。
